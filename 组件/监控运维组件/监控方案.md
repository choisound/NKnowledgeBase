# 监控方案

## 目标

为业务提供强有力的监控，业务异常时及时告警，提供高效可靠可视化页面，主要包括下面三个核心指标：

- **可见（Visibility）​**​：系统状态、核心链路、租户行为可量化、可查询。 
- **​可控（Controllability）​**​：出现异常时能自动响应，触发告警或限流等措施。 
- **​可回溯（Traceability）​**​：故障时可精准定位根因，回溯链路行为，审计变化历史。

## 主要挑战

-  **​多租户环境​**​：必须支持指标按​**​租户维度​**​（`tenant_id`）隔离、查询、归档。 
- **弹性计算结构​**​：服务实例动态伸缩，需具备强大的​**​服务发现与自动注册​**​能力。 
- **资源指标维度高​**​：CPU、内存、QPS、响应时间、链路深度、租户操作等维度需统一建模。 
- **租户 SLA 差异​**​：不同租户可能有差异化的告警敏感度与运营策略。 
- **非生产环境隔离​**​：测试/预发布环境指标需隔离监控，避免告警干扰主环境。

## 架构

实现一个完整的监控运营系统包含几大要素：数据采集、多维数据模型及指标定义、强大的查询语言及可视化、告警策略配置。其中，Prometheus是行业内生态好、使用范围广的组件，其整体架构图如下：

### 数据采集

####  Pull（拉取）模式（核心数据采集方式）

Prometheus Server 定期从配置好的目标（Target）的 HTTP API（通常是 `/metrics`接口）抓取指标数据。

##### 适用场景
**主流方式​**​，适用于可暴露HTTP端点、生命周期稳定的服务，如在线服务、常驻进程。

##### 相关组件（Exporter）
这是 Pull 模式中的关键组件。它就像一个“翻译官”，负责从那些原本不支持 Prometheus 格式的系统中（如操作系统、MySQL、Redis等）收集数据，并将其转换为 Prometheus 能够理解的格式，通过 HTTP 接口暴露出来。常见的 Exporter 有：
- •​**​Node Exporter​**​：用于采集服务器硬件和操作系统指标（如 CPU、内存、磁盘、网络）。 
- •其他众多针对数据库、中间件、网络设备的 Exporter。

#### Push（推送）模式（补充采集方式）
短生命周期的作业将指标数据​**​推送​**​到 Pushgateway 这个中间组件，Prometheus 再定期从 Pushgateway ​**​拉取​**​数据。

##### 适用场景
短生命周期任务（如批处理作业、定时脚本）、无法直接暴露端口的应用或第三方服务。

##### 相关组件（Pushgateway）
PushGateway 的核心是一个​**​中间代理和临时缓存层​**​。其基本工作模式如下：
1. ​**​数据推送（Push）​**​：各种短期作业、批处理任务或无法直接暴露 HTTP 端口的应用程序，通过 PushGateway 提供的 API，主动将监控指标数据以 HTTP POST 请求的形式推送到 PushGateway 服务器。 
2. ​**​数据暂存（Storage）​**​：PushGateway 接收到数据后，会将其存储在内存中。它也支持通过启动参数（如 `--persistence.file`）将数据持久化到磁盘文件，以防止服务重启造成数据丢失。 
3. ​**​数据拉取（Pull）​**​：Prometheus Server 仍然基于其固定的抓取间隔（scrape_interval），主动向 PushGateway 发起 HTTP GET 请求（默认获取 `/metrics`接口的数据），拉取已暂存的所有监控数据。​**​因此，从 Prometheus 的角度看，抓取 PushGateway 和抓取其他 Exporter 没有本质区别​**​，都是 Pull 模式。

#### 客户端嵌入应用

在应用程序代码中集成 Prometheus 客户端库，直接暴露监控指标。

##### 适用场景

需要深度定制和暴露应用内部指标的自研应用。

##### 组件库

Prometheus 官方提供的各种客户端库（如Go, Java, Python等）。

### 多维数据模型及指标定义（Metrics）

Prometheus 采集到数据后，其强大的查询和告警能力很大程度上依赖于规范、清晰的 Metrics。对 Metric 进行有效的清洗、管理和使用至关重要。

#### Metric 的清洗（Data Cleaning）

由于网络波动、应用异常或Exporter自身问题，Prometheus采集到的原始数据可能包含缺失、异常或格式不一致的情况。“清洗”旨在确保数据的质量和可靠性，为后续查询和告警提供准确的基础。

|​**​清洗类型​**​|​**​常见原因​**​|​**​处理方法与工具​**​|
|:-:|:-:|:-:|
|​**​处理缺失值​**​|监控目标短暂宕机、网络中断、Prometheus抓取间隔配置不当。|在应用层或查询层进行填充。PromQL的 `clamp_max()`、`clamp_min()`等函数可用来处理极端值。对于完全缺失的数据，有时需要在查询时使用 `OR`操作符或 `vector()`函数进行逻辑补全。|
|​**​处理异常值​**​|应用Bug、资源争用、Exporter指标上报逻辑错误（如返回`NaN`或`Inf`）。|利用PromQL函数（如`abs()`、`rate()`）结合布尔运算符进行过滤。例如：`my_metric{job="myjob"} > 0 and my_metric{job="myjob"} < 100`。|
|​**​数据格式化与标准化​**​|不同Exporter或应用版本输出的指标格式、标签不一致。|主要依靠​**​Relabeling​**​。在Prometheus的`scrape_config`中配置`relabel_configs`，可以重命名、修改、添加或删除标签，甚至根据标签值丢弃整个Metric。|

**其中Relabeling 是Prometheus数据清洗最核心的功能​**​，它允许你在抓取前后对指标标签进行动态修改。常见的Relabeling操作包括：
- 重命名标签（`action: replace`） 
- 只保留符合特定规则的目标（`action: keep`）或丢弃特定目标（`action: drop`） 
- 从现有标签创建新标签（使用`regex`进行分组提取）

#### Metric的管理

良好的Metric管理能提升查询效率、降低存储成本，并使监控系统更易于维护。
1. **规划与设计**
- 明确监控对象：遵循Google的“四个黄金指标”（延迟、流量、错误、饱和度） 。
- 设计规范的命名和标签：
 	- Metric命名：应包含​**​前缀​**​（表明所属领域，如`prometheus_`）、​**​主体​**​和​**​单位后缀​**​（如`_seconds_total`, `_bytes`）。使用基本单位（如`seconds`而非`milliseconds`） 。  
 	-  Label设计：确保同一Label下的数据单位统一，可平均或可加和。避免在Label中同时存储分项和总和（如`label=a`, `label=b`, `label=total`），总和应通过PromQL聚合计算得出。
2. **分类与使用​**
- **理解核心指标类型​**​
	- **​Counter​**​：只增不减的计数器，适用于请求数量、错误数量等。 
	- ​**​Gauge​**​：可增可减的仪表盘，适用于当前内存使用量、活跃连接数等。 
	- ​**​Histogram​**​：直方图，用于统计和分析数据的分布情况，如响应时间。 
	- ​**​Summary​**​：客户端计算的分位数，类似于Histogram。
- **合理选择Bucket​**​（针对Histogram）：根据数据分布和关注点设置合理的Bucket区间。例如，对于延迟指标，可以在P90、P95等关键分位数附近设置更密集的Bucket以获得更精确的分析。

3. **存储与保留​**

- **调整数据保留时间​**​：在Prometheus配置文件(`prometheus.yml`)中，通过`storage.tsdb.retention.time`参数设置数据保留策略（如`7d`）。Prometheus会自动删除过期数据。 
- **​使用分层存储​**​：对于需要长期存储的数据，可以集成​**​Thanos​**​或​**​Cortex​**​等方案，将数据压缩后存储到对象存储（如S3）中，以节省成本 。 
- **​手动清理数据​**​：在极端情况下，可以删除Prometheus的整个数据目录（`rm -rf /path/to/data/*`）或使用API删除特定序列，但​**​务必谨慎操作​**​  。

4. **常见的Saas服务层级指标**

|**层级​**​|​**​监控目标​**​|​**​关键指标​**​|​**​采集工具​**​|
|:-:|:-:|:-:|:-:|
|​**​IaaS 层​**​|云主机/虚拟机|CPU、内存、磁盘 I/O、网络流量|`node_exporter`|
|​**​PaaS 层​**​|Kubernetes/Docker|节点状态、Pod 状态、资源请求/限制|`kube-state-metrics`, `cAdvisor`|
|​**​SaaS 应用层​**​|微服务/应用|接口 QPS、延迟、错误率（4xx/5xx）|应用埋点（Micrometer, Prom Client）|
|​**​业务层​**​|租户/业务活动|注册数、订单数、支付成功率（按租户区分）|应用自定义埋点|
|​**​用户体验层​**​|可用性与体验|服务可用性（HTTP/S、TCP 探测）|`blackbox_exporter`|

### 强大的查询语言及可视化

#### 数据模型

Prometheus 的所有监控数据都存储为​**​时间序列（Time Series）​**​。每条时间序列由以下要素唯一确定：
1. ​**​指标名称（Metric Name）​**​：表明监控指标的含义，如 `http_requests_total`。它本质上是一个特殊的标签 `__name__` 。 
2. ​**​标签（Labels）​**​：一组键值对，提供了数据的多维特征（例如 `method="GET"`, `status="200"`, `instance="192.168.1.10:8080"`）。这是 Prometheus 实现多维查询和分析的核心 。 
3. ​**​样本（Sample）​**​：时间序列中的具体数据点，包含： - •​**​时间戳（Timestamp）​**​：一个精确到毫秒的 Unix 时间戳。  - •​**​样本值（Value）​**​：一个 float64 类型的浮点数，代表该时间点的测量值。   

其格式可表示为：`<metric name>{<label name>=<label value>, ...} <value> <timestamp>`
，例如 `http_requests_total{method="POST",status="200"} 42 1717182000000`。

##### 底层数据结构
为了高效存储和查询这些时间序列数据，Prometheus 的 TSDB（Time Series Database）采用了以下核心结构和机制：
###### 1. 内存中的结构（Head Block）

最近的数据（通常为2-3小时）被保存在内存中的 ​**​Head Block​**​ 以提高读写效率。
- **​Series 哈希表​**​：在内存中，所有活跃的时间序列都通过一个哈希表来管理，其中键由指标名称和标签集的哈希值生成，值指向对应的序列元数据（如标签列表）和最新的 Chunk 引用。这使得通过标签快速查找序列变得高效。 7  
- **​内存映射 Chunks​**​：Head Block 中的样本数据并非完全“裸”地在内存中，而是会映射到磁盘文件，这有助于减少内存占用。 7  

###### 2. 预写日志（WAL - Write-Ahead Log）

为防止数据丢失，所有样本数据在写入内存前会先追加写入 ​**​WAL​**​（一个只追加写的日志文件）。WAL 采用​**​分段文件设计​**​（默认每段128MB），并支持压缩（如 zstd, snappy）。这在系统发生崩溃时，可用于恢复尚未持久化到块的数据。

###### 3. 磁盘存储结构（Persistent Blocks）

数据最终会以只读的 ​**​Block​**​ 形式持久化到磁盘，每个 Block 默认包含约2小时的数据。
每个 Block 目录包含：
- **​`chunks/`目录​**​：存储实际压缩后的样本数据文件。每个文件包含多个 ​**​Chunk​**​，Chunk 是存储连续样本数据的基本单元。   
- **​`index`文件​**​：这是​**​倒排索引​**​的核心，用于快速根据指标名称和标签查找对应的 Chunk 及数据位置。它通常包含以下映射关系： 
 	- 指标名称 -> 对应的系列（Series） ‘
 	- 标签名 -> 标签值 -> 包含该标签的系列  
 	- 系列 -> 该系列所包含的 Chunk 的元信息（如时间范围、在 chunk 文件中的偏移量）   
- **​`meta.json`​**​：描述该 Block 的元数据，如时间范围、包含的系列数量、样本数等。 
- **​`tombstones`​**​：用于软删除（逻辑删除）。当需要删除某个时间范围内的数据时，会在此文件中记录删除标记，查询时会跳过这些数据。

###### 4. 数据压缩与编码

- **​Chunk 编码​**​：为节省空间，样本值会进行压缩编码。 
	- **​XOR Chunk​**​：最常用的编码方式。它对连续样本的时间戳和值进行
	- ​**​差分编码​**​（Delta-of-delta encoding for timestamps, XOR encoding for values），再使用变长编码压缩，显著减少存储空间。 
	-  **​Histogram Chunk​**​：专用于直方图类型指标的特殊编码。 
- **​块压缩（Compaction）​**​：TSDB 会定期将多个小的、时间上有重叠的 Block ​**​合并压缩​**​成更大的 Block。这个过程会移除已删除的数据，合并重复的样本，并重新生成索引，从而优化查询性能和存储空间。

### 💎 核心数据结构总结

下表概括了 Prometheus 底层的主要数据结构及其职责：

|​**​数据结构​**​|​**​存储位置​**​|​**​主要职责​**​|​**​关键特点​**​|
|:-:|:-:|:-:|:-:|
|​**​Series (元数据)​**​|内存 (Head) / 磁盘 (Block Index)|代表一个时间序列，存储标签列表。|通过哈希表快速查找，倒排索引支持多维查询。|
|​**​Chunk​**​|内存 (mmap) / 磁盘 (Block)|存储一个时间序列在某时间段内的连续样本值。|采用 XOR 等算法高效压缩，是数据存储的基本单元。|
|​**​WAL Segment​**​|磁盘|临时顺序记录写入的样本数据，用于崩溃恢复。|只追加写入，分段设计，支持压缩。|
|​**​Block Index​**​|磁盘 (Block)|提供从指标名称和标签到 Series 及 Chunk 的快速映射。|倒排索引结构，支持高效的多维数据过滤和查询。|
|​**​Tombstones​**​|磁盘 (Block)|记录 Block 中已被删除数据的时间范围。|逻辑删除，在压缩时物理清除。|
#### PromQL

PromQL 是 Prometheus 的查询语言，允许你​**​对时间序列数据进行灵活查询、聚合和计算​**​。

1. **核心数据类型​**​
	- **​瞬时向量​**​：特定时间点的一组时间序列值，适用于实时监控。 
	-  **​区间向量​**​：指定时间范围内的一组时间序列值，适用于趋势分析。  
	-  **​标量​**​：简单的数字浮点值。  
	-  **​字符串​**​：简单的字符串值（较少直接使用） 。   
2. ​**​关键操作符与函数​**​ PromQL 支持多种操作符和函数，以下是常见分类： 

|类型|操作符/函数|说明|示例|
|:-:|:-:|:-:|:-:|
|​**​比较运算符​**​|`==`, `!=`, `>`, `<`, `>=`, `<=`|用于过滤时间序列。|`http_requests_total{code="500"} > 100`|
|​**​逻辑运算符​**​|`and`, `or`, `unless`|用于组合多个查询条件。|`up{job="api"} == 1 and rate(http_requests_total[5m]) > 100`|
|​**​聚合操作符​**​|`sum()`, `avg()`, `min()`, `max()`, `count()`, `by()`|对时间序列进行聚合计算，`by`用于指定分组标签。|`sum(rate(http_requests_total[5m])) by (job, method)`|
|​**​常用函数​**​|`rate()`, `irate()`, `increase()`, `delta()`|计算时间序列的增长率、增量或差值。`rate()`适用于 Counter 类型指标。|`rate(node_cpu_seconds_total[5m])`|
||`histogram_quantile()`|计算直方图指标的分位数（如 P99）。|`histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))`|
||`predict_linear()`|基于历史数据进行线性预测。|`predict_linear(node_filesystem_free_bytes[2h], 4 * 3600)`|

3. ​**​查询与过滤​**​ - •使用 ​**​`{}`​**​ 和标签进行过滤，如 `http_requests_total{job="api-server", method="POST"}`。  - •支持 ​**​正则匹配​**​（`=~`, `!~`），如 `{job=~"mysql\|prometheus"}`  。

#### Grafana
Grafana 的强大功能得益于其精心设计的架构。
##### 1. 整体架构

Grafana 采用典型的前后端分离架构：
- **​前端​**​：主要使用 ​**​React​**​ 框架构建，负责用户界面的渲染和交互。提供了仪表盘、面板编辑器等用户界面组件 。 
- **​后端​**​：使用 ​**​Go 语言​**​（Golang）编写，提供 RESTful API，处理业务逻辑、认证、数据源代理、告警判断等任务。 
- **​数据库​**​：默认使用内嵌的 ​**​SQLite​**​，但也支持 PostgreSQL 或 MySQL 用于存储用户、仪表盘、数据源配置等元数据。

##### 3. 插件系统

Grafana 的强大扩展性源于其插件化架构：
- **​数据源插件​**​：允许 Grafana 连接和支持多种后端数据源（如 Prometheus, InfluxDB, Elasticsearch, MySQL 等）。每个数据源插件负责将 Grafana 的通用数据查询请求转换为该数据源的原生查询语言（如 PromQL）。 
- **​可视化面板插件​**​：提供除内置图表（如折线图、仪表盘、状态图）之外更丰富的图表类型（如热力图、地理地图、桑基图等）。 
- **​应用插件​**​：用于集成外部工具或提供更复杂的功能扩展。 

##### 4. 告警引擎

Grafana 的告警引擎主要工作流程如下：
1. ​**​定时评估​**​：告警引擎会根据规则中定义的频率（例如每 10 秒）周期性地执行配置的查询 。 
2. ​**​状态管理​**​：每条告警规则都有一个状态机（如 `OK`, `Pending`, `Firing`, `Error`）。当条件持续满足一定时间后，状态会从 `Pending`变为 `Firing`并发送通知。 
3. ​**​通知分发​**​：当警报触发时，引擎会根据配置，通过指定的通知渠道（如 Email, Slack, Webhook 等）发送告警信息，并支持告警静默和重试机制。 

#### 5. 性能优化机制

为保证处理大规模数据时的流畅性，Grafana 采用了多种优化策略：
- **​数据采样​**​：对大规模时序数据自动降采样，减少从数据源传输的数据量和前端渲染压力。 
- **​查询缓存​**​：对频繁访问的查询结果进行缓存，减少对数据源的直接查询次数。 
- **​懒加载​**​：只有当面板在浏览器可视区域内时，才会触发数据查询。

Prometheus 与 Grafana 的告警体系主要由以下组件协同工作：

|​**​组件​**​|​**​核心职责​**​|​**​关键特点​**​|
|:-:|:-:|:-:|
|​**​Prometheus Server​**​|1. 根据 `rule_files`配置，定期评估告警规则。<br>2. 当规则条件持续满足（`for`字段）时，将警报推送到 Alertmanager。|负责​**​产生警报​**​。|
|​**​Alertmanager​**​|1. 接收来自 Prometheus 的警报。<br>2. 对警报进行​**​分组​**​、​**​抑制​**​、​**​静默​**​，并​**​路由​**​到不同的接收器。<br>3. 通过多种渠道（如邮件、Slack、Webhook）发送告警通知。|负责​**​处理和管理警报​**​，是告警系统的“大脑”。|
|​**​Grafana​**​|1. 提供​**​可视化告警配置​**​界面（Alert Rule）。<br>2. 支持对面板直接创建告警，并​**​测试告警条件​**​。<br>3. 支持配置​**​通知渠道​**​（Contact Point）和​**​路由策略​**​（Notification Policy）。|提供​**​灵活的告警配置界面​**​和​**​可视化状态展示​**​。|
